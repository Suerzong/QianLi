# SO-ARM101 关节限位（2026-10-06 实测重标定）

> 本文件是限位的**权威记录**。上一版（2026-09-26）记的是舵机 EEPROM 的
> `Min/Max_Position_Limit`，那批值与实机零位不自洽（`elbow_flex` 当前
> 4047 远超它自己的 max 3069 也不报错），**不能当机械限位用**，已废弃。

## 为什么必须实测

`driver_params.yaml` 里的 `raw_min/raw_max` 曾经不是实测值，而是抄自
`lerobot-calibrate` 留下的 `my_so101_arm.json`。那份文件本身就有问题：

| 关节 | 旧 raw 范围 | 问题 |
|---|---|---|
| `shoulder_pan` | 826 ~ 3330 | 与 URDF 限位换算值**一模一样** → 是"照着 URDF 摆位"录的，不是推到死点录的 |
| `shoulder_lift` | 842 ~ 3118 | 同上 |
| `elbow_flex` | 2057 ~ 4095 | 上限被截到 4095 |
| `wrist_flex` | 954 ~ 3116 | 与 URDF 一致 |
| `wrist_roll` | **0 ~ 4095** | 明显是"没测，取默认" |
| `gripper` | 892 ~ 3168 | 下限与 URDF 不一致 |

于是软限位既不等于 URDF 设计意图，也不等于机械行程，而是**两边都不是**。
其中 `wrist_roll` 正向被 12 位量程截断，**吃掉 71.2° 行程** —— 这正是
"机械明明还有很大余量，软件却判危险区、直接吞掉"的主因。

## 实测方法

`joint_range_calibrate.py`：扭矩全部为 0（确认过 6 个舵机 `torque_enable=0`），
用手把每个关节推到**两个机械死点**，30 Hz 记录 `Present_Position`，
跨界自动按 4096 展开。150 秒采样 4431 次，0 读失败。
与 `lerobot-calibrate` 的手动校准流程一致（厂商手册 §4.1 也是"手动转动每个关节"）。

## 软限位规则

```
软限位 = min(URDF 设计意图, 机械死点 − 2.0°安全边距)
```

* URDF 比死点更保守 → 保留 URDF 的余量（那是设计者故意的，不是 bug）
* URDF 比死点更宽 → 必须收到死点以内，否则软件会命令舵机顶死

| 关节 | URDF 换算 | 机械死点−2° | 采用 | 哪侧被谁约束 |
|---|---|---|---|---|
| shoulder_pan | 826~3330 | 769~3276 | **826~3276** | 负向 URDF / 正向 机械 |
| shoulder_lift | 842~3118 | 807~3169 | **842~3118** | 两侧 URDF |
| elbow_flex | 1974~4178 | 1888~4061 | **1974~4061** | 负向 URDF / 正向 机械 |
| wrist_flex | 954~3116 | 854~3157 | **954~3116** | 两侧 URDF |
| wrist_roll | 1264~4905 → 重定零后 244~3885 | 146~3950 → 重定零后 124~3973 | **244~3885** | 两侧 URDF |
| gripper | 1916~3168 | 1944~3306 | **1944~3168** | 负向 机械 / 正向 URDF |

旧限位在 `shoulder_pan`、`elbow_flex`、`gripper` 上**越过了机械死点**，
即软件会命令舵机顶到硬限位（堵转、丢步、磨损）。

## wrist_roll 重新定零（这次修复的关键）

实测行程 338.3°，从 raw 1144 一直走到 **4993** —— 跨过了 4095 单圈边界。
而 `Goal_Position` 只有一个 12 位字，量程 `0..4095`。零位在 3053 时，
URDF 需要的窗口 `[1264, 4905]` 有 810 计数（71.2°）落在量程外。

旧代码的处理是**把 `raw_max` 截到 4095**，那 71.2° 就被静默吞掉了。
正确做法（lerobot `set_half_turn_homings()` 同款）是把整段行程平移进量程：

| | 值 |
|---|---|
| Homing_Offset | −1215 → **−195**（平移 −1020 计数 = −89.6°） |
| 当时 Present_Position | 4970 → **3950** |
| zero_raw | 3053 → **2033** |
| 机械行程 | [1144, 4993] → **[124, 3973]** |
| URDF 窗口 | [1264, 4905] → **[244, 3885]** |
| 软限位包络 | [−157.24°, +91.58°] → **[−157.24°, +162.77°]** |

**+71.2° 行程恢复。** 断电重启后 `Present_Position` 仍是 3950、
`Homing_Offset` 仍是 −195（EEPROM 已生效），说明新零位跨上电周期稳定 ——
这正是以前"回绕截断"的根源：旧零位让行程跨圈，上电后圈数解释就变了。

### Homing_Offset 的编码坑（实测确认）

Feetech 的 `Homing_Offset` **写入与回读用的编码不一样**：

* **写**：12 位"符号+幅值"，符号位 = bit 11
  （lerobot `feetech/tables.py`: `STS_SMS_SERIES_ENCODINGS_TABLE = {"Homing_Offset": 11}`）
  即 `-195` → `0x800 | 195 = 0x8C3`
* **读**：本机固件回的是 16 位**二进制补码**（−195 → `0xFF3D`）

按补码去写会得到完全不同的零位。判定成功与否**只看 `Present_Position`**，
并满足 `Present_Position = Actual_Position − Homing_Offset`（`Actual` 恒定）。
`servo_homing_shift.py` 已按此实现，并用闭环迭代校验。

| 错误标志位 | 0x01 电压 / 0x02 角度限位 / 0x04 过热 / 0x08 编码 / 0x10 力矩态 / 0x20 过载 |

## 维护注意

* **拆装关节、换舵机、换机械臂之后必须重测**，不要照抄本表。
* `driver_params.yaml` 有**两份**：源树和 `install/share`。
  `install` 那份是普通文件不是软链，launch 读它 —— 只改源码不生效。
* 重测流程：`joint_range_calibrate.py` → `derive_joint_limits.py`
  →（如需）`servo_homing_shift.py` → 覆盖两份 yaml → 看驱动启动时的包络表。
